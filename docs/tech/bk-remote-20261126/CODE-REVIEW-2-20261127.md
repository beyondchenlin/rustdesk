## 3. 实际发现与处理

### R2-01（问题编号）：托盘停止服务绕过确认

`src/tray.rs`（系统托盘）原有停止菜单直接调用 `uninstall_service(false, false)`（停止或卸载服务入口），没有设置页的确认流程。根代理已将停止菜单的创建及其事件处理共同限定为非 Windows（微软系统）编译分支；目标桌面仍保留打开菜单、左键打开和会话提示，底部设置页的原服务功能与二次确认保留。其他平台的原托盘行为保留。

独立复核同时检查了菜单创建与事件处理两段条件编译，避免只隐藏菜单、仍留相同事件处理。第五批桌面候选不包含此修复，第六批冻结包含；不能用第五批构建结果替代修复后的构建。

### R2-02（问题编号）：安卓兼容停止事件绕过确认

`flutter/lib/mobile/pages/server_page.dart`（安卓共享页）的 `stop_service`（停止服务事件）此前在已启动状态直接调用停止。当前悬浮窗已没有该事件的发送按钮，因此本问题属于仍可被分发的兼容处理入口，不能描述成现有可见按钮。

已改为保留“当前确实已启动”的守卫，再调用 `toggleService`（统一服务确认入口）。没有把“已停止时收到停止事件”变成启动。定向用例覆盖确认、取消、已停服务和实际方法分发；默认仍使用既有全局会话。

### R2-03（问题编号）：无归属投影取消误停既有接收服务

原生 `MainActivity.kt`（安卓主活动）在投影申请返回失败时向当前界面发送无请求编号的取消事件。旧界面销毁、新服务模型重建并收到 `service=true`（服务存在）以后，新的模型没有原来的“只申请投影”本地标志。旧处理把此取消当作首次启动失败，停止既有接收及文件会话。

已在 `server_model.dart`（服务模型）引入本模型首次启用归属及启用完成通知。无归属或仅投影申请的取消只清理申请状态，不停既有接收；属于本次首次启动的取消等待启用完成后再清理，避免晚到启用反向重开。真实投影成功清除首次申请归属；绑定尚未完成时早到的 `service=false`（服务暂未绑定）不误清归属。投影成功事件不再自动调用整服务启动。

已执行的 16 项生命周期回归覆盖原有 9 项及新增 7 项事件顺序，结果为 16 通过、0 失败；分析为 0 错误、0 警告。证据前缀为 `D:\demo2\bk-remote-toolchains\logs\client-lifecycle-ownership-20261127-225519`（定向生命周期检查）。这是界面与桥接时序回归，安卓 14/15（系统版本）的真实投影、锁屏、进程重建仍须现场验收。

### R2-04（问题编号）：明确停服与在途启用的顺序

进一步复核发现，投影取消已等待启用完成，但用户明确调用 `stopService`（停止服务）时未等待相同完成通知。原生 `main_start_service`（启用接收）确实写入空的 `stop-service`（停止接收配置）并重启登记；若它在停止调用之后才执行，能覆盖明确停服。

已修复并独立复核：原生停止标记保存成功后取消启动归属，等待已在途启用完成，再执行最后的原生停止。初次保存失败不提前关闭会话或丢失首次申请归属。

根代理追加检查的反向顺序也已收口：停止开始即占用独立完成通知，停止尚未完成时拒绝新的启动、投影或切换，不排队自动授权重启；只有停止等待旧启用，不存在反向互等。重复停止共享结果，但保留旧确认框后到的主动停服意图，并在结束前补做真实持久化。

进一步核实并修复部分成功的边界：自动原生清理已成功、后到主动标志保存失败时，不把界面恢复成已启用；继续完成旧启用收尾和原生接收关闭，再向所有共享调用者返回原错误。只有首次原生停止尚未成功的失败才恢复原状态。

最终定向回归为 27 项全部通过、0 失败、0 跳过，六文件分析 0 错误、0 警告、12 条信息；覆盖双向时序、默认取消、重复停止及部分成功后错误。证据前缀：`D:\demo2\bk-remote-toolchains\logs\client-stop-serialization-check-20261127-232756`（最终停止串行化检查）。前 16 项、18 项和本 27 项是逐次扩大同一组用例，不相加计数。

## 5. 三档案、账号与真实在线边界

`bk_profiles.rs`（档案核心）使用互斥的产品、自建手动和官方命名空间，进程启动时选择后保持不可变。设备身份、配置、对端凭据和账号缓存随命名空间隔离；选择记录同时使用代际，防止仅比较档案名称而接受旧进程响应。安卓在访问惰性配置及密钥缓存之前初始化档案；早期原生入口只安装独立回调与证书验证器状态，没有抢先初始化身份缓存。

`bk_profiles_windows.rs`（桌面档案交接）只操作产品服务；管理员提升取消不停止旧服务、不改选择、不提前停止原账号心跳。失败恢复保存事务开始前的原始选择，再提升代际；原来已经处于待恢复状态的记录不会被错误提升为稳定。新的登记循环会在配置尚未稳定时等待后重试，避免“进程启动成功但永久不登记”。旧进程看到代际不符退出，而不是在原进程热换账号和密钥。

桌面界面配置缓存不能当作后台接收服务的权威设置。`bk_service_settings.rs`（严格服务配置读取）在同一已鉴权主进程通信连接上读取前后档案探针、选项及代理；任一步失败、代际或路线不一致均拒绝，不回退本地旧副本。安卓读取当前本进程配置，并核验同一代际。

团队设备清单新增的原生在线查询没有把账号心跳换个名称冒充真实在线。它使用当前识别服务的签名响应，绑定随机挑战、精确设备顺序、数量和原位图；公钥错误、重放、篡改、超限、旧服务端不支持及查询失败均显示未知。观察时间来自本端验签成功时刻，“本端曾确认在线”与账号最后心跳分开，不编造服务端未提供的历史时间。

查询使用既有连接与代理路径，单个实际工作线程的许可持续保持到任务结束。界面 12 秒上限返回未知，即使底层同步域名解析仍未返回也不能启动无限数量的新线程。原生登记只证明识别服务中的有效登记租约，不等同于屏幕投影、输入授权或当前能够控制；系统权限独立展示与验收。

服务器对该查询使用现有识别服务私钥签名，不把管理员秘密放入客户端，也不宣称明文传输本身已加密。原辅助端口和旧客户端行为保留，新团队页不回落到未认证状态。详细线格式及验证见服务端 `docs/bk-remote/native-presence-protocol-v1.md`（签名登记查询协议）和 `native-presence-final-review-20261127.md`（最终服务端证据）。
