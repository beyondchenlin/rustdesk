## 4. 客户端品牌与默认配置

### 4.1 新安装默认值

现有客户端的密码策略代码位于 hbb_common 的 password_security 模块：
- approve-mode（连接批准方式）缺省时返回 Both（密码与点击确认）。
- verification-method（密码验证方式）缺省时返回 UseBothPasswords（固定密码与临时密码）。
- 这与 PRD 要求的新安装默认值不同。

最佳实现不是修改全局认证算法，也不是每次启动强制覆盖用户设置，而是使用 RustDesk 自带的 custom client config（定制客户端签名配置）：
- default-settings（默认配置）设置 approve-mode=password、verification-method=use-permanent-password。
- default-settings 只在用户没有自己的配置值时生效。
- 不使用 override-settings（强制覆盖配置），不锁死用户原有可选项。
- enable-keyboard（键盘鼠标输入）和 enable-file-transfer（文件传输）按 PRD 设置为新安装默认值；系统授权仍以真实状态为准。
- 自建模式默认填写 ID Server（设备识别服务）、API Server（账号接口服务）及公钥；Relay Server（中继服务）留空以跟随 hbbs 下发。

### 4.2 签名信任

当前源码 read_custom_client 使用固定的官方公钥验证 custom.txt。BK Remote 需要增加独立的 BK Remote 公钥信任入口，同时保留官方公钥验证能力：
- 公钥可以进入源码；私钥只存放在受保护的离线位置，不进入 Git、安装包、日志或构建缓存。
- Windows 使用随正式安装包部署的签名配置文件。
- Android 通过现有 FFI 初始化参数传入签名配置；必须验证安卓端确实加载了该配置。
- 测试签名正确、签名篡改、未知公钥、官方配置兼容四种情况。

### 4.3 三种服务器档案

必须实现独立档案，而不是只增加一个默认地址：
1. BK Remote：默认档案；ID Server 与 API Server 指向自建服务；Relay Server 留空，自动跟随服务器。
2. 官方公共服务器：恢复官方默认服务地址及独立账号环境。
3. 手动自建：保留原生 ID、Relay、API、公钥配置入口。

每个档案分别保存账号令牌、地址簿、设备身份和本机保存的连接凭据。切换档案不能把 BK Remote 的令牌或设备身份带入官方环境，也不能把官方账号数据带入 BK Remote。界面切换失败时恢复原档案，不自动降级到官方服务器。

APP_NAME（应用数据命名空间）可将 BK Remote 与官方 RustDesk 的数据目录分开；但单个 BK Remote 应用内仍需按服务器档案分区保存身份和账号数据，不能只依靠修改服务器地址。

## 5. 安卓服务生命周期

已核实源码链路：
- BootReceiver（开机广播接收器）只检查 KEY_START_ON_BOOT_OPT（开机启动选项）及系统权限，然后启动 MainService。
- BootReceiver 当前不检查用户主动停止服务的持久化标记。
- MainService.onStartCommand 返回 START_NOT_STICKY（不自动粘性重启）。
- MainService.destroy 会停止采集、释放 MediaProjection（屏幕投影）、停止前台服务、停止悬浮窗服务并调用 stopSelf。
- MainActivity 的 stop_service 通道最终调用 destroy。
- FloatingWindowService（悬浮窗服务）仍有 Stop service（停止服务）菜单入口；Flutter 页面也存在调用 stopService 的路径。

首版实施要求：
1. 区分结束当前会话、停止屏幕采集、停止整个接收服务、关闭开机启动。
2. 用户主动停止整个服务时，持久化 user_stopped 状态；BootReceiver 必须检查该状态。
3. 只有用户明确点击重新启动服务，才清除 user_stopped。
4. 屏幕采集开关不能误调用整服务 destroy。
5. 所有整服务停止入口统一移动到设置页底部危险操作区，二次确认；悬浮窗和共享页面不保留一触即停的整服务入口。
6. 不自动批准 Android（安卓）系统权限，不伪造 MediaProjection（屏幕投影）已授权状态。锁屏、重启、系统撤销权限均按实际系统结果显示。

## 6. 账号 API 与设备安全

### 6.1 选定的参考实现

使用 nntu 固定提交中的 rustdesk-api 后端作为候选基线，SQLite（轻量数据库）作为首版数据库：
- 配置默认 gorm.type=sqlite。
- SQLite 文件使用 WAL（预写日志）、busy_timeout=5000（忙等待 5 秒）及外键约束。
- SQLite 连接池最大打开连接被限制为 1，适合首版单实例小规模部署；扩容上限必须通过真实压测确定。
- API 后端许可证为 MIT；保留 LICENSE、版权声明和来源记录。
- 生产配置显式设置 app.register=false、app.web-client=0、app.show-swagger=0；不部署 rustdesk-api-web。
- 不部署 rustdesk-api-web，不把 nntu 的 1.1.15 hbbs/hbbr 覆盖当前 1.1.16。

### 6.2 已发现的安全阻塞

**阻塞 A：首次管理员密码写日志。**  
参考代码 DatabaseAutoUpdate 在首次迁移时自动创建 admin 用户，生成 8 位随机密码，并通过 Logger.Info 输出密码。该行为不符合 BK Remote 的安全要求。实施时必须删除自动创建默认管理员及明文日志路径，增加 bootstrap-admin（一次性管理员初始化）命令：仅当数据库没有管理员时执行，交互式输入密码、使用 bcrypt（密码哈希算法）保存、成功后拒绝再次初始化。公众注册保持 app.register=false。

**阻塞 B：部署令牌并非自动一次性。**  
DeployTokenTTLSeconds 为 30 分钟，令牌使用 24 字节随机数；FindValid 只检查是否使用及是否过期。现有 /api/devices/deploy 不自动消费令牌，通常要后续调用 /api/deploy/revoke 才标记 used_at。Consume 当前是先查询再更新，存在并发重复消费窗口。首版必须实现数据库原子消费、同设备幂等结果和审计；不得把 30 分钟有效期描述成已自动一次性使用。

**阻塞 C：设备登记没有设备私钥持有证明。**  
现有 Deploy 接口检查设备 ID 是否已归属其他用户，并接受客户端提交的 UUID、Pk；它没有对 Pk 对应私钥进行挑战签名验证，也没有完整处理 UUID/Pk 与其他设备记录的冲突。仅有账号令牌或部署令牌不能证明发起请求的客户端就是该设备。首版必须增加短时挑战及 Ed25519（椭圆曲线签名）持有证明，挑战绑定用户、设备 ID、UUID、公钥和有效期，并一次性使用。客户端签名使用设备本地私钥，服务端验证签名后再绑定归属。

**阻塞 D：公开 sysinfo 不是登记接口。**  
/api/sysinfo 未认证，可创建或更新设备信息记录；不得用它证明设备归属。未归属设备不能进入团队设备清单。

**阻塞 E：地址簿密码字段会存明文。**  
参考 DeviceCliForm 会把 AddressBookPassword 解码后写入 AddressBook.Password。首版禁止用该路径同步设备固定密码；AddressBook.Password、日志、接口响应及缓存均不得携带固定密码。跨主控端凭据同步不在首版实现。

### 6.3 账号与权限规则

- app.register=false（关闭公众注册）；启动配置校验及未认证注册请求测试均必须通过。
- 首次管理员只由 bootstrap-admin 命令建立；之后通过已认证管理员 API 创建普通账号。
- JWT（身份令牌）签名密钥使用高熵随机值，仅存服务端环境变量或受保护配置，不进入客户端包和仓库。
- 用户登录、设备归属、设备固定密码是三个独立权限层。
- 当前选定的 rustdesk-server 1.1.16 源码没有 MUST_LOGIN/JWT 强制登录门禁；首版不移植 nntu 的强制登录门禁，保留原生无账号手动连接。若未来引入登录门禁，必须单独设计和评审。
- 撤销账号或设备必须使 API 令牌失效并更新授权关系；目标设备离线时标记待撤销，不报已完成。
- 设备固定密码独立随机、独立设置；首次连接仍使用原生认证，不因同账号而绕过。

## 7. 动态中继管理

### 7.1 当前服务端真实行为

当前服务端代码已确认：
- 启动参数支持 relay-servers（中继节点列表）。
- 运行时命令 rs 可向 hbbs 发送新的中继节点列表。
- 多节点按轮询分配，不是按延迟择优。
- 每约 3 秒执行一次节点检查，使用 FramedStream（协议帧连接）探测，单节点超时 3 秒。
- 当所有新节点都探测失败时，检查逻辑不会用空列表覆盖最后一组非空活动列表，因此可能继续保留旧节点。
- 运行时 rs 命令只改进程内状态，不负责持久化启动配置。
- 本地命令控制通道使用 NAT 辅助端口 21115 的 loopback（本机回环）连接；外部来源按原生 NAT/在线查询协议处理。

### 7.2 发布管理流程

新增本机 bk-remote-relayctl（中继管理命令）：
1. 校验节点格式、域名解析、端口、公钥和节点状态。
2. 先对候选节点执行协议级连通探测；记录时间、结果和耗时。
3. 至少一个候选节点通过后，生成带版本号的候选配置。
4. 原子写入持久化配置文件并保留上一有效版本。
5. 通过 127.0.0.1:21115 发送 rs 命令更新 hbbs 运行时节点池。
6. 再次查询运行时列表，等待健康检查结果并逐项核对。
7. 验证通过才标记发布成功；失败则恢复上一持久化配置并重新下发。
8. 全部节点失败时显示降级、保留旧配置、告警；不能把旧列表误报为新列表健康。

本机控制端口不得映射到公网，不得由未授权远程 HTTP 请求转发调用。生产部署前必须确认实际服务管理器、启动参数和持久化配置路径；本轮不触碰现有香港服务器。

## 8. 接口与数据边界

首版 API 复用参考项目的登录、用户、地址簿和设备列表契约；新增安全设备登记挑战接口及原子令牌消费逻辑。固定客户端版本后冻结请求/响应字段。

| 数据 | 存储规则 |
|---|---|
| 用户密码 | 服务端 bcrypt 哈希，不返回明文 |
| API 令牌 | 仅客户端安全存储和服务端必要令牌表，不写日志 |
| 设备 ID/UUID/公钥 | 服务端设备表，登记时验证冲突及私钥持有证明 |
| 设备固定密码 | 不进入团队地址簿、API 同步负载、日志或截图 |
| 设备状态 | 心跳时间、在线来源、最后确认时间；查询失败标记未知 |
| 中继配置 | 版本、节点、健康探测、发布人、发布时间、回滚版本 |
| 审计 | 登录、设备加入/撤销、账号停用、中继发布/回滚；不记录屏幕内容、剪贴板和密码 |
